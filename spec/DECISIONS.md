# Decisions

Choices made where the design is silent. One line each: the choice and the reason.

- Hashes in trace columns are bare lowercase blake3 hex. Fields the design shows with a prefix (state `digest`, action `inputs`) use `blake3:<hex>` via `hashing.prefixed`. Reason: one representation per column, and the prefix only where the design shows it.
- CIFS refusal in `Store.open` reads `/proc/mounts` and refuses `cifs`, `smb3`, `smbfs` for the longest mount prefix of the database path. Reason: no subprocess, no extra dependency; `stat -f` gives the same answer.
- `schema.sql` is migration version 1 and is applied with `CREATE ... IF NOT EXISTS`; later migrations are `db/migrations/NNNN_name.sql`, forward-only. Reason: simplest runner that records what was applied.
- Timestamps are UTC ISO 8601 with a Z suffix at second precision. Reason: sortable as text, no timezone ambiguity.
- `holds` carries the binding columns (`bound_*`) and a `context_json` in addition to the design's list, so rebind lookup (7.4) can compare a new hold to prior reviews without recomputing bindings. `run_id` on `holds` is nullable for the project-level init confirm. Reason: the design says holds are bound; this is where the bindings live before a review exists.
- `actions` carries `param_source_json` and `ticket` as columns because design 5 lists them on the Action record. `runs` carries a reserved `budgets_json` (design 17). `artifacts` carries `name` and `status` (`produced | rejected`) so a post-gate block can quarantine outputs (6.2). `judgments` carries `attempt`.
- Init-time predicate verdicts are recorded in `predicate_results` with `run_id = 'init'` and `action_id = project_id`; the column has no foreign key to `runs` for that reason. Reason: the design records every verdict, and init has no run.
- A failed `init` removes what it created (only when the target directory did not exist or was empty), so the same path can be re-initialised after the cause is fixed. Its verdicts are printed, not stored. Reason: a half-bound directory would otherwise block re-init forever.
- Method repos hold one version of each module: `modules/<name>/module.yml` whose `version` must equal the version the pipeline asks for. Reason: the repo is pinned by tag, so one version per name suffices; a mismatch is a lint error with a clear message.
- The design's `units.observation` names the row itself and is not required to be a column; every other unit, factor column, and batch variable is (`init.column_missing`). Reason: matches the design's example, where `observation: cell` is not an obs column.
- `init.reference_mismatch` compares an input's optional `build` against the pipeline's optional `reference_build`, and passes when either is absent. Reason: the design names the check but not the fields; these are the minimum.
- The init `confirm` hold is a `holds` row with `run_id` and `step_id` NULL, `waits_on_role: owner`, bound to the blake3 of the three declaration files' hashes. `Project.confirm_status()` reopens a fresh hold (and rewrites `echo.md`) when the declarations change. Reason: 2.7 says the accept is bound to the file hashes.
- Judgment modules declare a `consensus` output (`type: consensus, format: json`) that the engine writes; downstream steps reference `$steps.<id>.consensus`, never `judgments`. Reason: 8.4 says downstream consumes consensus only, and refs must resolve to a declared output.
- Module scripts receive one JSON job on stdin: `{inputs: {name: path}, params, outputs: {name: path}, output_dir, seed}`. `.py` runs under the engine's interpreter, `.R` under Rscript, `.sh` under bash. Reason: 3.4 says "a JSON job on stdin"; the shape is the simplest that carries everything.
- A predicate that raises or exceeds its five-second budget is recorded as fired with the error as its reason. Reason: a broken check must not read as a passed one.
- Predicate scope entries: `*`, an operation name, `kind:<kind>`, `runner:<runner>`, `stochastic:true`, `considered_set:true`, `project` (init). Reason: the design's scope column mixes operations, module kinds, and runner; this encodes each without a second mechanism.
- Lint's "replicates below the policy minimum" uses the `standard` profile's `replicates_min`. Reason: lint has no project profile; standard is the deployment default.
- The module manifest carries `params_schema` (loaded from `params.schema.json` by `load_module`) so predicates can read declared parameters from the context without I/O. Reason: predicates are pure.
- Lint warns about an unlisted in-scope predicate only when the predicate's scope is narrower than `*`. Reason: every module would otherwise carry every engine predicate in `gates:`, which defeats the declaration's purpose.
- Numerals in rationale and prose are matched with a regex that excludes digits adjacent to word characters (so `cluster_7` and `CD8A` are not claims). Report prose is checked against every cell of the module's evidence tables; rationale against the item's cited values. Reason: 8.3 specifies the rounding rule, not the tokenizer.
- `param.out_of_range` resolves to `flag` under a profile with `params: free` inside `Policy.effective`, after overrides and before the remap. Reason: 6.5 states the rule; the policy file has no other way to express it per-parameter-mode.
- The ticket issued by `propose` is the action id, stored in `actions.ticket` when the step's runner is operator; `submit` looks the action up by ticket and requires the step to be `awaiting_execution`. Reason: actions are append-only, so the ticket must be known when the row is written; validity comes from the step status.
- Operator-supplied outputs are copied into `runs/<run>/<step>/` and hashed there; evidence files are copied under `evidence/`. Reason: the run directory is the durable record and the sidecar must sit beside the file it describes.
- The pre-state of a step is the snapshot of the most recently completed step in the run (or the run's initial snapshot). Snapshots of rejected or failed steps stay in the trace and are never a pre-state. Reason: a rejected step's output is not admissible as input to anything downstream (6.2), including the next attempt's gate.
- `run` does not require `method/` HEAD to equal the SHA bound at init; it records the SHA per run. Reason: 6.3 and 6.7 say the way past a block is to commit and run again.
- The toy `policy.yml` overrides `repro.env_unverified` to `log` under standard and exploratory, leaving `flag` under strict. Reason: toy scripts run outside containers; the trace still records `as_reported` and the coverage report lists it.
- Under the engine runner, a run-open with a missing environment digest is recorded as `unpinned` and blocked by `repro.env_unpinned` at the first pre-gate rather than refused at open. Reason: the build plan's M5 acceptance asks for the block; the run record still shows the missing digest.
- Mock harness fixtures are YAML rules keyed by item, replicate, and template (module name, template hash, or `*`), with optional `when` conditions on evidence cells; evidence-ref values and `{column}` placeholders in rationales are filled from the evidence the request carried. Fixture path from `STRINGENCY_MOCK_FIXTURE` or `.stringency/mock.yml`; family from `STRINGENCY_MOCK_FAMILY`. Reason: the build plan keys fixtures by template hash, item, and replicate; letting values follow the data keeps `judg.evidence_exists` honest under the mock and lets the negative control abstain on shuffled input without a second fixture.
- `Request` carries the evidence tables in memory for the mock only; request files written for subagents contain the prompt, schema, nonce, and response path and nothing else. Reason: the session agent must never handle the prompt or the evidence.
- Under `all_items` batching the response schema is `{items: [<schema.json>]}` with `$defs` hoisted so `#/$defs/...` references resolve. Reason: one prompt for all items needs an array envelope; the module's schema stays the item schema.
- In the direct family a response that fails validation is retried once with the errors appended; both invocations are recorded. In the dispatch family there is no retry: a missing, unparseable, nonce-mismatched, or invalid response marks the replicate invalid. Reason: 3.5 step 4 and 10.2.
- Judgment steps write `judgments.jsonl` (every valid replicate's items, with `replicate`) and `consensus.json`; item holds and flag holds are settled together, so a step with any open hold is `held`. Reason: 8.4 says an unresolved item cannot exist in a completed step.

# Decisions

Choices made where the design is silent. One line each: the choice and the reason.

- Hashes in trace columns are bare lowercase blake3 hex. Fields the design shows with a prefix (state `digest`, action `inputs`) use `blake3:<hex>` via `hashing.prefixed`. Reason: one representation per column, and the prefix only where the design shows it.
- CIFS refusal in `Store.open` reads `/proc/mounts` and refuses `cifs`, `smb3`, `smbfs` for the longest mount prefix of the database path. Reason: no subprocess, no extra dependency; `stat -f` gives the same answer.
- `schema.sql` is migration version 1 and is applied with `CREATE ... IF NOT EXISTS`; later migrations are `db/migrations/NNNN_name.sql`, forward-only. Reason: simplest runner that records what was applied.
- Timestamps are UTC ISO 8601 with a Z suffix at second precision. Reason: sortable as text, no timezone ambiguity.
- `holds` carries the binding columns (`bound_*`) and a `context_json` in addition to the design's list, so rebind lookup (7.4) can compare a new hold to prior reviews without recomputing bindings. `run_id` on `holds` is nullable for the project-level init confirm. Reason: the design says holds are bound; this is where the bindings live before a review exists.
- `actions` carries `param_source_json` and `ticket` as columns because design 5 lists them on the Action record. `runs` carries a reserved `budgets_json` (design 17). `artifacts` carries `name` and `status` (`produced | rejected`) so a post-gate block can quarantine outputs (6.2). `judgments` carries `attempt`.
- Init-time predicate verdicts are recorded in `predicate_results` with `run_id = 'init'` and `action_id = project_id`; the column has no foreign key to `runs` for that reason. Reason: the design records every verdict, and init has no run.
- A failed `init` removes what it created (only when the target directory did not exist or was empty), so the same path can be re-initialised after the cause is fixed. Its verdicts are printed, not stored. Reason: a half-bound directory would otherwise block re-init forever.
- Method repos hold one version of each module: `modules/<name>/module.yml` whose `version` must equal the version the pipeline asks for. Reason: the repo is pinned by tag, so one version per name suffices; a mismatch is a lint error with a clear message.
- The design's `units.observation` names the row itself and is not required to be a column; every other unit, factor column, and batch variable is (`init.column_missing`). Reason: matches the design's example, where `observation: cell` is not an obs column.
- `init.reference_mismatch` compares an input's optional `build` against the pipeline's optional `reference_build`, and passes when either is absent. Reason: the design names the check but not the fields; these are the minimum.
- The init `confirm` hold is a `holds` row with `run_id` and `step_id` NULL, `waits_on_role: owner`, bound to the blake3 of the three declaration files' hashes. `Project.confirm_status()` reopens a fresh hold (and rewrites `echo.md`) when the declarations change. Reason: 2.7 says the accept is bound to the file hashes.
- Judgment modules declare a `consensus` output (`type: consensus, format: json`) that the engine writes; downstream steps reference `$steps.<id>.consensus`, never `judgments`. Reason: 8.4 says downstream consumes consensus only, and refs must resolve to a declared output.
- Module scripts receive one JSON job on stdin: `{inputs: {name: path}, params, outputs: {name: path}, output_dir, seed}`. `.py` runs under the engine's interpreter, `.R` under Rscript, `.sh` under bash. Reason: 3.4 says "a JSON job on stdin"; the shape is the simplest that carries everything.
- A predicate that raises or exceeds its five-second budget is recorded as fired with the error as its reason. Reason: a broken check must not read as a passed one.
- Predicate scope entries: `*`, an operation name, `kind:<kind>`, `runner:<runner>`, `stochastic:true`, `considered_set:true`, `project` (init). Reason: the design's scope column mixes operations, module kinds, and runner; this encodes each without a second mechanism.
- Lint's "replicates below the policy minimum" uses the `standard` profile's `replicates_min`. Reason: lint has no project profile; standard is the deployment default.
- The module manifest carries `params_schema` (loaded from `params.schema.json` by `load_module`) so predicates can read declared parameters from the context without I/O. Reason: predicates are pure.
- Lint warns about an unlisted in-scope predicate only when the predicate's scope is narrower than `*`. Reason: every module would otherwise carry every engine predicate in `gates:`, which defeats the declaration's purpose.
- Numerals in rationale and prose are matched with a regex that excludes digits adjacent to word characters (so `cluster_7` and `CD8A` are not claims). Report prose is checked against every cell of the module's evidence tables; rationale against the item's cited values. Reason: 8.3 specifies the rounding rule, not the tokenizer.
- `param.out_of_range` resolves to `flag` under a profile with `params: free` inside `Policy.effective`, after overrides and before the remap. Reason: 6.5 states the rule; the policy file has no other way to express it per-parameter-mode.
- The ticket issued by `propose` is the action id, stored in `actions.ticket` when the step's runner is operator; `submit` looks the action up by ticket and requires the step to be `awaiting_execution`. Reason: actions are append-only, so the ticket must be known when the row is written; validity comes from the step status.
- Operator-supplied outputs are copied into `runs/<run>/<step>/` and hashed there; evidence files are copied under `evidence/`. Reason: the run directory is the durable record and the sidecar must sit beside the file it describes.
- The pre-state of a step is the snapshot of the most recently completed step in the run (or the run's initial snapshot). Snapshots of rejected or failed steps stay in the trace and are never a pre-state. Reason: a rejected step's output is not admissible as input to anything downstream (6.2), including the next attempt's gate.
- `run` does not require `method/` HEAD to equal the SHA bound at init; it records the SHA per run. Reason: 6.3 and 6.7 say the way past a block is to commit and run again.
- The toy `policy.yml` overrides `repro.env_unverified` to `log` under standard and exploratory, leaving `flag` under strict. Reason: toy scripts run outside containers; the trace still records `as_reported` and the coverage report lists it.
- Under the engine runner, a run-open with a missing environment digest is recorded as `unpinned` and blocked by `repro.env_unpinned` at the first pre-gate rather than refused at open. Reason: the build plan's M5 acceptance asks for the block; the run record still shows the missing digest.
- Mock harness fixtures are YAML rules keyed by item, replicate, and template (module name, template hash, or `*`), with optional `when` conditions on evidence cells; evidence-ref values and `{column}` placeholders in rationales are filled from the evidence the request carried. Fixture path from `STRINGENCY_MOCK_FIXTURE` or `.stringency/mock.yml`; family from `STRINGENCY_MOCK_FAMILY`. Reason: the build plan keys fixtures by template hash, item, and replicate; letting values follow the data keeps `judg.evidence_exists` honest under the mock and lets the negative control abstain on shuffled input without a second fixture.
- `Request` carries the evidence tables in memory for the mock only; request files written for subagents contain the prompt, schema, nonce, and response path and nothing else. Reason: the session agent must never handle the prompt or the evidence.
- Under `all_items` batching the response schema is `{items: [<schema.json>]}` with `$defs` hoisted so `#/$defs/...` references resolve. Reason: one prompt for all items needs an array envelope; the module's schema stays the item schema.
- In the direct family a response that fails validation is retried once with the errors appended; both invocations are recorded. In the dispatch family there is no retry: a missing, unparseable, nonce-mismatched, or invalid response marks the replicate invalid. Reason: 3.5 step 4 and 10.2.
- Judgment steps write `judgments.jsonl` (every valid replicate's items, with `replicate`) and `consensus.json`; item holds and flag holds are settled together, so a step with any open hold is `held`. Reason: 8.4 says an unresolved item cannot exist in a completed step.
- Judgment modules are always engine-run whatever the project's `execution` or the step's `runner`. Reason: 3.5 step 2 and 10.3 say evidence generation and harness calls are made by the engine.
- `submit` settles its step and reports what comes next but does not advance the run; the agent calls `run` again, which proposes the next step (exit 21) or dispatches (exit 20). Reason: 14.1 keeps `run` as the loop and `submit` as one verb.
- `run` collects dispatch responses when any response file exists (or when the mock is in dispatch mode); with none present it reports `dispatching` again (exit 20). Reason: the operator may call `run` before the subagents finish.
- `runs/<run_id>/summary.md` is written whenever `run` finds the run complete, including when the last step's completion already derived the status. Reason: the summary is part of the run record (2.1).
- `review` without `--verdict` prints the queue (oldest first, the project confirm hold first) with each hold's evidence; verdicts are given non-interactively with `--verdict --hold ...`. Reason: the CLI is driven by agents and skill wrappers as often as by a person; a prompt loop would block them.
- `via` is `tty` only when both stdin and stdout are terminals; otherwise `--attest` is required and records `relayed`. Reason: 7.5.
- Accepting an item hold picks a replicate's call; when every non-abstaining replicate agrees `--replicate` may be omitted, otherwise it is required. Reason: 7.3 says accept takes a chosen replicate; the shortcut covers the self_uncertain case where the calls already agree.
- Review reasons are also written to `prov/justifications/<review_id>.md`. Reason: design 2.1 lists the directory.
- `deliver` marks final: every report-module output, every output named as a deliverable in the objective, and anything passed with `--include`. Files land in `deliver/<run_id>/` as `<step_id>.<name>.<ext>` with their sidecars, plus `coverage.md`, `coverage.json`, `methods.md`, `index.json`. Reason: 12.1 names report outputs as the default; deliverables must be present, so they are harvested too.
- A final artifact is an orphan when its sidecar is missing or its recorded hash disagrees with the sidecar. Reason: 9.6; a sidecar that describes a different file is no better than none.
- Coverage counts a decision point as covered when any predicate evaluated for that step declares `covers` for `operation.param` or `operation.*`; `in scope` counts predicates whose scope matches any step of the pipeline in either phase. Reason: 6.6.
- `runs` carries `kind` (`run | control`); control runs are excluded from `latest_run`, so `run` never resumes one. Reason: 11 says controls run in an isolated context through the same trace machinery; the same database keeps them queryable for the coverage report.
- A control's pipeline is the bound pipeline's steps up to and including the module's step, every step engine-run, with the object input of the fixture's type rewired to `control_input`. Reason: a judgment module's evidence comes from upstream steps; the control must reproduce them from the fixture, and the design names only the fixture and the module.
- Control expectations are evaluated from the trace (`judgments`, `consensus`), not from the step status, so a negative control whose abstentions create holds still scores. `planted` controls are recorded with their `detect_at` but not scored until a plugin supplies a truth table (the toy has none). Reason: build plan M10 covers negative and positive; the planted rule needs the generator's truth.
- The regression diff compares against the last passing result for the same module version and control: a lower agreement, a higher abstain rate on a positive control, or a lost null output is a regression. Reason: 11 says the diff is the regression test; these are the directions that matter.
- A fork copies the parent's artifact rows (pointing at the parent's files) and writes an inherited initial snapshot whose history entries carry `inherited: true`; `--set` keys are `<step>.<param>` at or after `--at` and are applied when `run` proposes that step. Reason: 2.6 and 4.3.
- The `api` harness uses `client.messages.create` with `output_config.format` of type `json_schema` carrying the module's schema, model `claude-opus-5` by default (overridable per module with `model:`), thinking left at the model default, and records the response's `model`, `usage`, and a `refusal` stop reason as an error. Reason: the current SDK's structured-output mechanism, read at build time; the design says record the resolved model and never guess.
- The apptainer executor reports an environment digest only when the manifest's sha256 matches the SIF on disk; it binds every input directory and the step directory and runs with `--containall --pwd <step dir>`. Reason: 10.3.
- The singlecell skeleton lives in a separate repository (`../stringency-singlecell`) and depends on the engine through a `tool.uv.sources` git URL; the engine test that checks both plugins appear in `plugins list` skips when the skeleton is not installed. Reason: the build plan wants a separate repo and CI for the engine must not depend on it.
\n- `interpreter_for` names interpreters portably (`python3`, `Rscript`, `bash`); the local executor resolves `python3` to the engine's own interpreter, and the apptainer executor binds the directory of every existing absolute path in the command and in `stdin_json` in addition to the declared binds and the working directory. Reason: under `--containall` the host venv and the plugin's tool scripts are invisible; the first init with `--executor apptainer` on BMESEQ (2026-09-08) failed with the container unable to stat the host Python. Call sites stay unchanged.
- The apptainer executor uses `apptainer` when present, else `singularity` (identical command line), and `STRINGENCY_APPTAINER_BIN` overrides both; the executions row records the command actually run. Reason: BMESEQ ships singularity-ce under the old name; the design names the family, not the binary.
- `scripts/install.sh` installs the engine into `/usr/local/lib/stringency/versions/<version>` with a `current` symlink and an `envs/` directory for images, and `integrations/claude-science/` holds a generic operator skill and its publishing notes. Reason: the Claude Science sandbox mounts granted paths and `/usr/local` but not home directories, so a per-user install is invisible to it; the design's method-specific skill wrappers (10.4) still belong to method repos.
- Deferred (design 17, 2026-09-08): a reviewer-run local review page as a third `via` value equivalent to `tty`. Reason: relayed review is the only non-terminal path and is deliberately weaker; a page served by the reviewer's own process keeps the agent out of the verdict without new dependencies. Not built until a non-terminal reviewer exists.
- The review display (7.3) lives in `review_render.py`, one renderer per hold kind, and is the same object `review`, `review --json`, and the later on-disk packet read. Cited cells are shown resolved against the evidence table (`table[row].column = stored`, or `cited x, stored y` when they differ); rationales are quoted; for `judg.*` flags every (replicate, item) the predicate reported is shown with its judgment row and, for `judg.confidence_consistent`, the policy criterion it failed. The display states what each verdict does and never recommends one. Reason: the first real flag hold (2026-09-08) took four files to answer; the design promises the content, not counts.
- `review --hold <id>` without `--verdict` shows that one hold, open or resolved. Every hold message (`run`, `next`, `init`, `status`, the confirm refusal) names the hold id and that command. Reason: 14.2 says the message names the hold and the one command; `review` alone lists the whole queue.
- `init` exits 10 when it leaves its confirm hold open, after printing the project record (JSON included). Reason: 14.2; `run` on the same hold already exits 10, and a wrapper should not need to special-case `init`.
- Mock fixture evidence refs may be dicts (`{row: C, column: mean_value}`); table and row default to the item's, and a missing value is filled from the evidence. Reason: replaying the toy-cs judges, who cited other rows' cells as contradicting evidence, needs cross-row refs; `tests/fixtures/harness/context_contradicting.yml` is that regression fixture.
- When a ticket is issued (`propose`, or `run` reaching an operator step, or a pre-hold accepted on one) the engine creates the step directory and writes `job.json` there: the same stdin it would feed the script itself. The job spec (`propose`, `next --json`) carries `exec`, the executor's exact command line with stdin from `job.json` and both streams to the declared job log, and `submit`, the exact submit line with concrete output and evidence paths and `--command` quoting `exec`. `job.json` is a ticket artifact like a dispatch request and has no sidecar. Reason: the exit run's operator assembled all three by hand (B1); one source of truth for the command is `Executor.command_line`, which `run` also uses.
- `submit --command "<string>"` records the operator's own account of what it ran in `executions.command`; like every field on an operator row it is as reported. Reason: C2; the invocation was otherwise lost.
- `executions.env_digest` is set only when `env_status` is `verified`; the digest the run resolved for the env goes in the new `expected_env_digest` column (migration `0002`). The coverage report is unchanged. Reason: C1; an as-reported row carrying the expected digest read as verified.
- `status --json` lists every open hold, the project-level confirm hold included, with id, kind, step, item, role and user, and the human output names `review --hold <id>` for each. Reason: B2.
- `run` refuses with exit 16 when the latest run is closed and names `run --new`, which opens the next run; `--new` on an open run is refused too. `propose` and `submit` inherit the refusal, so neither can open a run by accident. Reason: B3; a `run` typed after the final submit opened a second attempt in the exit run. Design 2.6 and 14.1 updated.
- Every rendered judgment prompt ends with `prompting.evidence_suffix`: the definition of `supporting_evidence` (cells arguing for the chosen label) and `contradicting_evidence` (cells arguing against it), context cells in neither, and the bound policy's confidence criteria spelled out. `spec/module-contract.md` carries the same definition. The predicate stays mechanical. Reason: D1; all three toy-cs judges filed context cells as contradicting and fired `judg.confidence_consistent`. The toy prompt says the same in its own words; label-groups is 0.1.1.
- The toy operator modules (filter-rows, summarize-groups, toy-report) declare `apptainer_inspect` evidence at `inspect.json` beside the job log, and are 0.1.1; both toy pipelines are 0.1.1. The ticket carries `evidence_commands`: for `apptainer_inspect`, `{ <binary> inspect --json <image>; sha256sum <image>; } > <step>/inspect.json`, since a pulled SIF's labels carry no digest of the file; the parser reads the checksum line, `env_status` verifies it against the manifest, and `exec.plan_drift` rejects a digest that disagrees. Evidence the executor cannot produce (no image under the local executor) is left out of the printed submit line with a note. Reason: C3; the exit run never exercised env verification on operator steps.
- `env_status` treats a reported container digest as decisive: equal to the manifest's sha256 is `verified`, different is `as_reported` even when the image path or name matches; the name route applies only when no digest was reported. Reason: the checksum line names the image path, so a wrong digest beside the right path verified by name (found by the C3 test).
- When a step is held the engine writes a review packet per open hold, `runs/<run>/<step>/review/<hold_id>.md` and `.html` (jinja2, inline CSS, no scripts), whose content is the `review` render verbatim; the `run` hold message and `review --json` name the Markdown path. The project confirm hold has no packet (`echo.md` is it). Packets carry no sidecar: a derived view, not an output. Reason: review-ux layer 2 (A4); a reviewer without a terminal can read the hold over scp or as a saved artifact; the verdict still goes in by terminal or relay.
- Run open captures the blake3 of every module entry script on disk (`run_events` `captures`.`script_blobs`, keyed by module ref); the engine hashes the script again before it runs one and at `submit` for an operator step, stores it in `executions.script_blob` (migration `0003`), and `exec.script_drift@1` (post, scope `*`, block) fires when the two differ. Comparing against the tree at open rather than the commit makes `--allow-dirty` runs consistent: the dirty flag and reason describe that tree. Judgment modules have no script and are exempt; runs opened before the capture existed have no blobs and are not checked. Reason: `repro.dirty_tree` only sees the tree at open, so a script edited between open and execution ran under the run's SHA unrecorded (found 2026-09-09).
- The methods paragraph spells counts out up to ninety-nine (the predicate count opens a sentence). Reason: the toy pipeline now evaluates twenty-one predicates and a sentence should not begin with a numeral.
- `declare --check <dir>` runs `init`'s whole path in a temporary directory (clone, schema, hashes, extractor pass, `init.*` predicates, echo-back) and removes it; exit 0 with the echo-back or 15 naming the failure. Reason: the drafting loop needs the checks without a half-created project; one code path, stopped before the project record.
- `init --drafted-by person|agent --brief <file>`: `stringency.yml` gains a `declarations` block (`drafted_by`, `harness`, `session_ref`, `brief`), the brief is copied to `brief.md`, and the confirm hold context carries `drafted_by`, `brief`, and `brief_blake3`. Editing the brief later does not reopen the hold; the declarations are the binding. Reason: spec/plans/declarations-and-objectives.md part 1; the same distinction `proposed_by` makes for actions.
- An input item may carry `derived_from: {run_id, step_id, output, project}`; `init` verifies run, step, output name, and hash against the sidecar beside the file. The note proposed `artifact_id`; sidecars carry `step_id` and `name` and not the artifact id, so those are the keys. Run open captures the list under `captures.derived_from`; the methods paragraph names the upstream run. Reason: option 1 of the objectives note, chained projects, with the chain verified rather than asserted.
- `plugins list --json` exposes `design_schema` and `vocabulary_terms` per plugin. Reason: the declare skill needs them and should not read plugin source.
- The toy plugin gains the question `process_rows` and the pipeline `toy-process` (filter only, deliverable `object`) so a two-project chain is testable; plugin version 0.1.1. Reason: the toy must exercise chained projects before application 1 does.
- `lint` accepts `<repo-or-url>@<tag>` as `init` does, cloning the tag into a temporary directory before linting; a plain path still lints in place. Reason: the declare skill lints the method it is about to bind, and the spec string is what it has.
- `run --json` carries `completed_steps`, the steps this invocation ran to completion on the engine, in order; the human output prints them on one line before the stop message. Reason: an operator reading "ticket for step 2" with no word about step 1 reported step 1 as skipped; the trace knew better and now the output says so.
- `Plugin` gains an optional `defaults` mapping (declaration values the plugin publishes, such as `min_n_per_group`), shown by `plugins list` and its `--json`. The toy publishes `min_n_per_group: 2`; plugin 0.1.2. Reason: the drafting skill asked for a default twice because none was published; the engine's own default (0) is not a scientific default.
- The echo-back pluralises the replication unit ("at least 2 units per group"). Reason: grammar; the echo is read aloud to a person.
- `render_brief.py` takes `--image` (repeatable) so an unbound project's probe checks the image, and `--declare` so Phase 1 hands over to the declare skill instead of running `init` on hand-written files. Reason: both were patched by hand for the PROTSEQ run.
- `steps[].title` is an optional plain phrase on a pipeline step; `Pipeline.title(step_id)` falls back to the id, so nothing that renders titles needs a null check; `next --json` and `run --json` carry `title` beside `job_spec` and `dispatch_dir`, and `plan.title` for a runnable step, so the operator's intent sentence names the step without reading the pipeline file. `lint` warns, not errors, when a method repo has `skills/<pipeline>.yml` and the pipeline leaves steps untitled: a pipeline with an analysis skill is read by a lay person, one without may not be. Reason: ux-two-audiences 3.2; a missing title degrades the sentence, it does not break the trace.
- The job spec gains `operator_line`: `exec`, then every producible evidence command, then `submit`, joined by ` && `; null when the module has no script (`exec` is null). The schema string stays `stringency.job_spec/1`. Reason: 3.2; one string is one approval card, and `&&` stops at the first failing part so a failed exec never reaches `submit`.
- `run --responses <file|->` files one document `{"step_id", "responses": [...]}` to `resp_N.json` in manifest order and then runs the loop, which collects as before. It refuses with exit 16 when no step is dispatching, when the document names another step, when the count differs from `manifest.json`, or when any response file already exists (never overwrites); a malformed document is exit 15. The document's `step_id` is required so a stale document cannot land on the wrong step. Reason: 3.2; the 10.2 file contract and nonce check are untouched, the flag only replaces the operator's per-file writes.
- `run --deliver` delivers only when the loop returned `completed` and the run's status is `completed`; a stop at `--until`, a hold, or a ticket delivers nothing and the payload has no `delivery` key. Reason: 3.2; `deliver` refuses on anything but a completed run, and a flag should not turn that refusal into an error on an otherwise normal stop.
- `plain` (`src/stringency/plain.py`) is two sentences on one line: progress ("Completed: <titles>." or "No step has completed.") from the run's step statuses in pipeline order, then one stop sentence per `Next.kind`; counts are spelled out; `status --json` renders the same sentences from the same `next` reading, says "The run was abandoned." for an abandoned run, and "No run has started." (plus the confirm hold) before one. `status --json` also carries `completed_steps`, every completed step of the run in pipeline order; on `run --json` the same key means the steps this invocation completed (Track 0). Reason: 3.2 and 6; the progress sentence is what a lay reader asked for and the stop sentence is the one line a skill relays without composing prose from codes. Goldens: `tests/golden/plain_*.txt`, one per kind plus the variants (confirm hold, several holds, one request, `--until`, waiting on a predecessor).
- `--attest` is refused (exit 16) when `STRINGENCY_SESSION_REF` is unset, before anything is written; `web` and `tty` are unaffected. `reviews.operator_harness` (migration `0004`, additive) is filled from `STRINGENCY_OPERATOR` on every review, null when unset. Reason: design 7.5 as amended 2026-09-15; a relayed verdict names its session and its harness.
- `deliver` writes `summary.md` (`src/stringency/summary.py`) beside the other three files and lists it in `index.json`; the `deliveries` row is unchanged (no new column). Sections as in ux-two-audiences 6. "What was analyzed" is the echo-back without its heading, its acceptance instruction, and the hash block. "What ran" lists parameters whose `param_source` is not `default` as "k set to v", else "at defaults" or "no parameters". "What you received" names each file with its output name, the step title, and the module's declared type and format, because `IOSpec` has no description field and adding one would touch the frozen module contract; if a description is wanted it is a contract question for the owner. Zero counts in the judgment line read "none". Reason: design 12.1 amendment; the reader of this page never opens the trace, so every sentence is filled from it and nothing is added.
- The toy pipelines `toy`, `toy-engine`, `toy-process` carry titles ("Filter low-value rows", "Summarize each group", "Label the groups", "Compare the groups", "Write the report") and are all 0.1.2; modules are unchanged. Reason: 3.2; the plain sentences and `summary.md` goldens need titles, and the method repo mirrors the plugin template.
- `init.column_missing` skips an input declared with `derived_from`. Reason: design 566 says "absent from the raw input"; a chained input is a delivered artifact whose columns are the upstream module's output, and the design columns were checked against the raw inputs at the upstream project's init. Found 2026-09-18 when the cross-region `qc_metrics_all` table (no `condition` column) was bound into the outlier judgment.
- `stringency board` and `stringency present` read `stringency.yml`, the trace and the pipeline file directly (`present.Site`) and never construct a `Project`, so they need no plugin installed and never open or resolve a hold. The board's `STATUS.md` is rewritten by `init`, `run`, `propose`, `submit`, `review`, `deliver` and `abandon` only when the file already exists beside the projects, and a failure to rewrite it never fails the verb. Reason: a reading verb must work from any install and must not change state; the board is a convenience the operator turns on once.
- The delivery skill `skills/<pipeline>.yml` lives in the method repository, not the plugin or the engine: the method knows what its outputs mean. The engine only renders (`table`, `json_table`, `jsonl`, `text`, `file`), degrades to a default on any malformed skill, and echoes `never_show` as a rule for the operator rather than enforcing it. Reason: 10.4 says the analysis skill is the method's; the engine adding prose of its own would be a second author.

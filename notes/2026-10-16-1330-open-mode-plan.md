# The open-mode plan (2026-10-16)

## Goal

The owner, after the commons assessment of the same day: pipeline mode serves the upstream
half of the work (raw data to a reliable dataset); the downstream half (questions of that
dataset) is non-linear and needs something like commons. Plan a second mode in which the
operator answers a person's questions with trusted tools shipped with the method or with
model-written code the engine labels untested, switching automatically after a delivery.

## Done

- Three read-only explorations of the engine (modes and profiles and the deferred open mode;
  delivery, console and skills; modules, plugins, controls, executors and the bulk and spatial
  plans) and three design passes (the smallest engine change; the person's and the method
  author's experience; where rigor leaks), then one plan.
- The owner's five decisions, asked and answered: model-written code runs under the engine's
  executor (`exec`; this answers G2); the first real target after the toy is Lyons CLP Xenium;
  the operator's reply text is gated (every numeral must match a cited cell); the switch is one
  relayed yes on a pinned paragraph, not an inherited confirmation; delivery from an open run
  never stops for a sign-off (the rerun counts and the labels are the record).
- One change the owner asked for at approval: before the switch the operator reviews the
  tools the method ships and the questions the project declared (`tools list --context`: the
  tools with their words, the objective's question and deliverables, the design's factors) and
  proposes three to five paths forward, each marked as a tool (would be trusted) or code (would
  be untested); a picked path is filed as the first question with `origin: suggested`.
- The plan, approved: `spec/plans/open_mode_plan.md` (the owner filed it; this session added
  the Status line). Row in `spec/README.md`; Lane K in `roadmap-2026-10.md`; G2 answered in
  `backlog.md`.
- Implementation started here (S1 binding) and stopped at the owner's instruction: the work
  will be driven by an agent on the lab's workstation against the installed engine. The
  parallel session card for O1 (the skill text) was withdrawn for the same reason. No engine
  file was changed.

## Learned

- The design already says what open mode is: design 5, "the agent proposes the operation as
  well as the parameters, using the same record"; `actions` needs no migration. The code refuses
  it in exactly two places (`config.py` and `project.init_project`).
- `module.yml` already carries `modes` (default `[pipeline]`), read by lint and
  `topo.undeclared_step` and nothing else, so a trusted tool is a module listing `open` and
  the frozen module contract is untouched; the words a tool needs for the person go in the
  skill files.
- `steps` rows exist only for `pipeline.yml` steps, created at run open, so on-demand steps are
  the one structural addition: a synthetic `StepDecl` at proposal and a `RunContext.pipeline`
  that grows. Every predicate, the planner, the executor, holds and artifacts then work as they
  are.
- `judg.numeric_claims_match` already runs on `type: prose` outputs, but against every cell of
  every evidence table; an answer must be checked against the cited cells, because any numeral
  matches something in a ten-thousand-row table.
- `deliver` evaluates its gate with `store=None` and reads only `gate.blocked`, so its verdicts
  are dropped; `job_for` binds every input directory read-write, so a session script could
  overwrite the delivery; `Job.timeout` is never set; the apptainer command carries no `--net`.
  All four are in the plan's containment list.
- The control scorer for a deterministic module checks only that the step completed; a tool
  needs a truth-table expectation (`expect.equals`) before "trusted" means anything.
- The exit-code set is frozen with no room, so the new verbs reuse 0, 10, 11, 12, 13, 15, 16.
